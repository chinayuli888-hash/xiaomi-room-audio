# 0.7.0 预览版验收

日期：2026-11-21。范围：Windows 本机、同日同一局域网中的两台小米 Sound 与一台 Sound Pro。本页仅记录本轮检查，不包含本机网络地址、设备身份或用户自定义比例值。

## 功能与自动化检查

**最终 82 项测试通过**，结果为 `Ran 82 tests … OK`。覆盖发现与列表生命周期、稳定身份选择、比例跨重启保存、静音与零总音量下保留比例、损坏档案和保存失败保护、比例限幅、退出恢复及节拍逻辑等。

真实 GUI 操作确认：

- 在三台已发现设备中取消 Pro，重新扫描后显示两台参与，实际 TCP 会话只连接黑、白两台 Sound。
- 正常退出并重新打开，界面保留“选择 2/3”以及先前保存的比例。
- 验收结束后恢复原来的三台参与设置，保留用户当时自定义的新比例，没有公开其具体数值。
- 正常停止与退出恢复原来的电脑播放输出。Ctrl+Q 与窗口、托盘退出共用正常停播流程。

受控脚本主音量按 2% → 4% → 2% 调整，各路发送增益最高约 4%，电脑输出最高 5%；GUI 中读到的单台最高设置为 7%，验收操作均不超过 10%。这些是软件音量设置，不是声压测量。

## 采集与节拍数据

最终实现采用 Windows QPC / `perf_counter()` 与高精度 sleep。控制查询移入独立 COM 监控线程，每包发送热路径不做 COM 查询。采集缓冲仍为 **15 包**，容量没有增大。

旧版三路对照采集 10,485,216 字节。两路 GUI 测试从开始到首份 PCM 约 **2,020 ms**；这是冷启动取得音频数据的时间，不是端到端声学延迟。

队列丢弃与源欠载是两种计数：前者是采集积压时丢弃的 PCM 字节，后者是发送端当时没有取得可用 PCM。它们都不是逐台声学录音结论。

## 已知限制

- 只有两次受控短测得到队列丢弃为 0，真实 GUI 和交互测试仍有丢弃；**不能宣传零丢帧、无断点或已通过长期稳定性验收**。
- 冷启动仍可能等待首份 PCM，并出现源欠载；三路与两路的部分后续窗口也有欠载。队列丢弃为 0 不表示这些问题不存在。
- 本轮没有重新录音测端到端延迟、逐台测 TDOA、真实切换 Wi-Fi 或做长时运行验证。早期约 0.69 秒录音结果保留在历史说明中，不能当作本版新测量。
- 连接与发送计数不能证明每台音箱的实际声学到达时间一致，也不代表各房间相同百分比具有相同声压。

## 发布内容

本预览版提供源码 ZIP、使用说明、验收摘要与 SHA-256 清单四个附件。Python、VB-CABLE、FFmpeg 及通过 pip 安装的运行依赖需另行准备，不捆绑这些运行环境或安装包。
